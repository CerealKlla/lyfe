# Lyfe

Player-centric RPG progression mod for a modular Minecraft project (Minecraft Java Edition). Part of the same suite as Cartographyr — owns the player (skills, XP, levels, subjective world knowledge); Cartographyr owns objective world truths. Lyfe treats Cartographyr as an optional soft dependency: most skills work standalone, but Cartographyr-requiring skills (named after that dependency, e.g. the "Cartographyr" skill) are entirely absent from the skill tree when Cartographyr isn't loaded.

## Context directory — read this first

`context/` is a **separate private repo** (https://github.com/CerealKlla/lyfe-context), not part of this one — it's listed in `.gitignore` here and must never be committed to this repo. It's cloned as a subdirectory at `context/` for local convenience. If this directory is missing (e.g. a fresh clone of just this repo), restore it with:

```
git clone https://github.com/CerealKlla/lyfe-context.git context
```

- `context/design-document.md` — the authoritative design spec. Start here for anything about intended shape or scope.
- `context/decisions.md` — dated log of decisions made during implementation that extend or override the design document, with rationale.
- `context/classes/` — one short markdown file per implemented class: public surface, key state, collaborators. Read the relevant file here before opening the actual source, and before editing a class update its file to match.

**Keep this system current as you work:**
- When a design decision is made that conflicts with or is absent from design-document.md, update design-document.md directly and add a dated entry to decisions.md explaining the change.
- When a class is added or its public surface changes, add or update its file in `context/classes/`.
- Don't let source and these docs drift — treat updating them as part of finishing the change, not optional cleanup.
- `context/` has its own git history, independent of this repo's commits. Commit and push changes there separately (`git -C context add . && git -C context commit -m "..." && git -C context push`) — editing the files alone doesn't back them up.

**Section 10 (Survivalist & Cook) designed and implemented 2026-09-24** (Phase 2.5) — see [context/decisions.md](context/decisions.md). New `.hunger` package, built as a direct port of vanilla's own `FoodData#tick` (found in the decompiled source, not assumed): `PlayerHunger` holds true hunger/saturation; `HungerListener` pins vanilla's real food level to a constant `17` every tick (between the sprint and regen thresholds, below the "still hungry" cutoff so real eating still works), mirrors real point-losses 1:1 (absolute, not scaled) onto the true number, and replicates vanilla's exact regen tiers/starvation/sprint-lock against that true number using vanilla's own fixed constants — except the fast-regen "are you full" check, which is deliberately relative to the player's own grown max, not a fixed 20 (a judgment call, flagged in decisions.md). Cook (renamed from the old "Chef" placeholder) boosts cooked-food restoration, XP'd on eating a cooked item specifically (a filled-in assumption — "XP from cooking" was considered and rejected over multiplayer furnace-ownership ambiguity). 6 new unit tests for `PlayerHunger`'s pure clamping logic; the tick/eating mechanism itself isn't unit-testable (needs a live `ServerPlayer`). Boot-smoke-tested clean via `runServer`/`runClient`; **in-game behavior (eating, regen, starvation, sprint-lock, overlay look) not yet confirmed**. This work also inserted a new Section 10 into design-document.md and renumbered everything after it (old 10→11 through 15→16) — see decisions.md for the full mapping before trusting an old cross-reference's section number.

**Second round of Survivalist/Cook playtest fixes, 2026-09-24** — see [context/decisions.md](context/decisions.md). Real in-game testing surfaced four issues, three fixed:
- **Attachment sync bug (real, affected every skill)**: mutating an object returned by `getData()` does not trigger a client resync in NeoForge — only `setData`/`removeData` do. This silently broke the hunger overlay and likely Lumberjack/Miner's `SpeedMultiplier` too, undetected until now. Fixed by adding explicit `player.syncData(...)` calls after every in-place mutation of `PLAYER_HUNGER` (`HungerListener`, `DebugCommands`) and `PLAYER_SKILLS` (centrally in `api.Lyfe#addXp`, covering all skills at once).
- **Full-eating not blocked**: decoupling hunger broke vanilla's own "can't eat when full" check, since it only ever sees the pinned real food level. Fixed with a new `HungerListener#onUseItemStart` that cancels `LivingEntityUseItemEvent.Start` for non-`canAlwaysEat()` food at true-max.
- **Burn-kill Cook XP attribution**: originally checked the killing blow's damage-source entity, which misses "ignited with Fire Aspect, then died later purely from burning" (no entity on that final source). Fixed to use `LivingEntity#getLastHurtByPlayer()` — vanilla's own general kill-credit tracking (100-tick memory), which covers this case correctly.
- **Not fixed, documented as a known limitation**: the hunger overlay's icons overlap the oxygen bubble HUD while swimming. Vanilla positions air bubbles via a private, stateful field (`Gui#rightHeight`) that only vanilla's own HUD layers coordinate through — a custom `GuiLayer` can't participate without also replacing air-bubble rendering. Deferred, tied to a future **Swimmer** skill (more bubbles past vanilla's cap, swim speed) that would need the same custom-overlay treatment `HungerOverlay` uses.
- Debug commands (`/lyfe xp`, `/lyfe hunger`) also stopped working mid-testing; root cause pragmatically resolved by lowering `DebugCommands`' permission from gamemaster to `LEVEL_ALL` rather than continuing to chase why `ops.json` didn't take effect as expected — see decisions.md for the full debugging trail.

**Confirmed live, 2026-09-24**: `/lyfe` commands work and the burn-then-later-death Cook XP trigger fires correctly. Survivalist & Cook (Phase 2.5) considered done for now; the oxygen-bubble overlap remains an open, documented limitation deferred to a future Swimmer skill.

**Maps now auto-render as real vanilla filled maps, 2026-09-24** (see [context/decisions.md](context/decisions.md), [context/classes/TerrainMapRenderer.md](context/classes/TerrainMapRenderer.md)) — the map branch of `SignListener.handleSubmit` no longer inserts a plain placeholder item; it resolves the target's real dimension, builds a genuine `Items.FILLED_MAP` via `MapItem.create`, and fills its full 128x128 grid in one synchronous pass using a new `TerrainMapRenderer`, a port of vanilla's own `MapItem#update` per-cell sampling/coloring logic (dominant `MapColor` via a Guava `Multiset`, water-depth/height-diff `Brightness`) with the player-relative/incremental-only parts (radius, per-tick throttling, dithering, ceiling-dimension case) dropped in favor of a one-shot full-grid fill. **Whole-tree-clear branch bug fixed, per-skill whole-structure-chance caps, 2026-09-25** (see [context/decisions.md](context/decisions.md)) — playtest report: chopping a whole tree left branch logs behind. Root cause (found via a read-only Explore subagent investigation): `WholeStructureClear`'s flood-fill only checked the 6 face-adjacent neighbors, but vanilla branch logs sit diagonally offset from the trunk, so they were simply unreachable — fixed by widening to all 26 neighbors in the surrounding 3x3x3 cube. Miner shares this exact algorithm and had the identical latent limitation, just rarely noticeable since ore veins tend to be compact/face-connected already — fixed for both at once. Separately, `GatheringListener`'s whole-structure-chance curve (previously one shared 10%-at-level-50 curve for both skills) split into two: Lumberjack caps at 20% at level 50, Miner at 30%, per the user's request. `./gradlew build`/`test` green, boot-smoke-tested clean. **Live in-game confirmation (chop a branchy tree, check the new chance caps feel right) is still pending.**

**Cartographyr skill fleshed out: distance, writer XP/attribution, 10-level curve, rotation slop, 2026-09-25** (see [context/decisions.md](context/decisions.md)) — the user's own playtesting flagged that signs only ever showed distance for `EXACT` knowledge, even though most real knowledge is less precise. Built out in one pass: `KnowledgeReference` gained a `writerId`, so `handleRead` can now credit Cartographyr XP back to whoever wrote a sign/map when someone else learns from it — **including if the writer is offline**, via a new `api.Lyfe#addXp(MinecraftServer, UUID, SkillId, long)` that loads/saves an offline player's attachment data directly via `PlayerDataStorage` + a scratch `FakePlayer` (researched against the decompiled source first, confirmed this uses the exact same attachment-persistence codec path as the online case, not a shortcut). New `DistanceText` shows a sign's distance in feet/miles (1 block = 1 meter), fuzzed by knowledge completeness, gated to writer level 2+; sign rotation gets a matching random slop for imprecise knowledge, both rolled once at write time. Cartographyr also got its own dedicated 10-level curve (previously shared a 1-50 curve with Historian).

**Location knowledge reworked into a real KnowledgeFactor set; creation XP restricted to maps, same day** (see [context/decisions.md](context/decisions.md)) — two corrections from the user before testing the above: (1) the old single-tier `LocationPrecision` (RELATIVE/APPROXIMATE/EXACT) wasn't meant to stay as an "interim mapping" for distance variance — knowledge is now really tracked as a `Set<KnowledgeFactor>` (`DIRECTION`/`DISTANCE`/`POSITION`), each independently worth 10% accuracy, purely additive (`PlayerKnowledge#learnLocationFactors`), reaching exact (0% variance) once all three are known; `LocationPrecision` was deleted entirely. (2) Creation XP was meant for **maps only** — a bound sign, once broken, drops back to a completely ordinary reusable vanilla sign item, so granting XP there would allow infinite free farming by breaking/rebinding the same sign; a map consumes a real, non-recoverable item and can't be re-targeted once bound. Material cost factoring into XP balance is now a standing design principle, not just this one fix. `./gradlew build`/`test` green (tests rewritten for the new model), boot-smoke-tested clean.

**First live playtest round: eight fixes, 2026-09-25** (see [context/decisions.md](context/decisions.md)) — the KnowledgeFactor mechanic finally got a real `runClient` playtest, unblocked by two new debug commands (`/lyfe knowledge learn <x> <z> <count>`, then `/lyfe knowledge learnrandom <count>` — needed because there was previously no way to reach a genuinely *partial* knowledge state solo). **Location overlay staleness bug fixed, same day** (see [context/decisions.md](context/decisions.md)) — playtest report: entering a cherry blossom biome, the overlay's location never updated, and stayed wrong through death/respawn and even a full relog. Two bugs: (1) cherry groves had no biome profile in Cartographyr at all (fixed there, see that repo's decisions.md); (2) the real bug — `LocationTracker#onPlayerTick`/`onPlayerLoggedIn` both silently skipped sending any update whenever nothing was detected, instead of letting the overlay correctly clear. That's also why relogging didn't help: the client's overlay state isn't reset by reconnecting, and the server-side bug meant it never got told to clear either. Fixed by removing both early returns — an empty detection result now always flows through and correctly blanks the overlay once confirmed (existing debounce logic handles it with no special-casing). `./gradlew build`/`test` green.
