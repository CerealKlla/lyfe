# Lyfe

Player-centric RPG progression mod for a modular Minecraft project (Minecraft Java Edition). Part of the same suite as Cartographyr — owns the player (skills, XP, levels, subjective world knowledge); Cartographyr owns objective world truths. Lyfe treats Cartographyr as an optional soft dependency: most skills work standalone, but Cartographyr-requiring skills (named after that dependency, e.g. the "Cartographyr" skill) are entirely absent from the skill tree when Cartographyr isn't loaded.

## Context directory — read this first

`context/` is a **separate private repo** (https://github.com/CerealKlla/lyfe-context), not part of this one — it's listed in `.gitignore` here and must never be committed to this repo. It's cloned as a subdirectory at `context/` for local convenience. If this directory is missing (e.g. a fresh clone of just this repo), restore it with:

```
git clone https://github.com/CerealKlla/lyfe-context.git context
```

- `context/design-document.md` — the authoritative design spec. Start here for anything about intended shape or scope.
- `context/decisions.md` — dated log of decisions made during implementation that extend or override the design document, with rationale.
- `context/classes/` — one short markdown file per implemented class: public surface, key state, collaborators. Read the relevant file here before opening the actual source, and before editing a class update its file to match.

**Keep this system current as you work:**
- When a design decision is made that conflicts with or is absent from design-document.md, update design-document.md directly and add a dated entry to decisions.md explaining the change.
- When a class is added or its public surface changes, add or update its file in `context/classes/`.
- Don't let source and these docs drift — treat updating them as part of finishing the change, not optional cleanup.
- `context/` has its own git history, independent of this repo's commits. Commit and push changes there separately (`git -C context add . && git -C context commit -m "..." && git -C context push`) — editing the files alone doesn't back them up.

## Status

Project scaffolded (NeoForge 26.1.2.109 / JDK 25, mirroring Cartographyr's toolchain exactly). `neoforge.mods.toml` declares Cartographyr as an optional soft dependency per Section 8 (no `versionRange` field — an empty string there is an invalid range that makes FML reject an installed Cartographyr outright, not "accept any version"; confirmed via a failed boot test, 2026-09-24).

**Phase 1 (Core Skill Data Model) implemented, 2026-09-24** — see [context/decisions.md](context/decisions.md):
- `.skill` package: `SkillId`, `SkillCategory`, `EffectType`, `SkillEffect`, `XpCurve`, `SkillDefinition`, `SkillRegistry` (in-memory, soft-dependency-aware `available()` filtering for Section 8).
- `.data.PlayerSkills` — per-player XP, persisted via NeoForge's Data Attachment API, schema-versioned `MapCodec`.
- `.registration.ModAttachments` — the `DeferredRegister<AttachmentType<?>>`.
- `.api.Lyfe` — the stable public facade (`getXp`/`addXp`/`getLevel`/`getAvailableSkills`), mirrors Cartographyr's `Cartography` facade pattern.
- Lumberjack and Miner registered as `SkillDefinition`s (id/category/curve) with an intentionally empty effects list — the Section 6 tool-tier gates are Phase 2 work (need real vanilla `Tiers` mapping + block-break event hooks), not invented ahead of that.
- 12 unit tests (XP curve math, effect stacking, registry filtering, attachment codec round-trip). Boot-smoke-tested via `runServer` with both Cartographyr and Lyfe loaded.

**Phase 2 (Lumberjack & Miner) implemented 2026-09-24, minus tool-tier gating** — see [context/decisions.md](context/decisions.md):
- New `.gathering` package: `GatheringSkill` (block -> Lumberjack/Miner via `BlockTags.LOGS`/NeoForge's `Tags.Blocks.ORES`), `WholeStructureClear` (pure flood-fill, needs a live level so not unit-tested — same limitation as Cartographyr's `NaturalRegionDiscovery`), `GatheringListener` (the event wiring: `BlockDropsEvent` for XP/bonus-yield/whole-structure-clear, `PlayerEvent.BreakSpeed` for speed scaling).
- `PLAYER_SKILLS` attachment now also syncs to the client (`ModAttachments`) — needed because `Player#getDestroySpeed` runs both sides.
- **Tool-tier gating (Section 7) is deliberately NOT implemented** — deferred until the crafting overhaul (Section 10) has a concrete tool-tier design to gate against; `EffectType.TOOL_TIER_GATE` carries a doc comment explaining this so it doesn't read as an oversight.
- **Anti-farming (added 2026-09-24, surfaced by playtesting)**: `PlacedGatheringBlocks` tracks exact positions of player-placed logs/ores; breaking one still drops the item normally but grants no XP/bonus-yield/whole-structure-chance. Placed blocks are also immovable by pistons (scoped to tracked positions only, not a blanket rule) to close the piston-laundering variant.
- Boot-smoke-tested via `runServer` with both mods loaded, clean.

**`.location` package added 2026-09-24** (see [context/decisions.md](context/decisions.md)) — the persistent "Location: <name>" HUD overlay, moved here from Cartographyr at the user's request: a location readout is player knowledge/belief, not world truth, so it belongs in Lyfe. `LocationTracker` (tick-based detection/debounce, ported from Cartographyr's old code) reads Cartographyr's public `Cartography` API only; `LocationPayload`/`ClientLocationState`/`LocationOverlay` handle the sync+display, with a mostly-solid dark background per request. **First real compile-time dependency on Cartographyr's Java API** — `compileOnly files("../Cartographyr/build/libs/...")` in `build.gradle`, kept off the runtime classpath; actual optionality enforced by only constructing/registering `LocationTracker` behind `ModList.get().isLoaded("cartographyr")` in `LyfeMod`. Verified boot-clean both with and without Cartographyr present. Still an honest simplification — mirrors Cartographyr's live truth on a timer, not yet gated by/recorded into a real persisted player-knowledge store (Section 9.3, still just a design-doc table, no code yet).

**Section 10 (Survivalist & Cook) designed and implemented 2026-09-24** (Phase 2.5) — see [context/decisions.md](context/decisions.md). New `.hunger` package, built as a direct port of vanilla's own `FoodData#tick` (found in the decompiled source, not assumed): `PlayerHunger` holds true hunger/saturation; `HungerListener` pins vanilla's real food level to a constant `17` every tick (between the sprint and regen thresholds, below the "still hungry" cutoff so real eating still works), mirrors real point-losses 1:1 (absolute, not scaled) onto the true number, and replicates vanilla's exact regen tiers/starvation/sprint-lock against that true number using vanilla's own fixed constants — except the fast-regen "are you full" check, which is deliberately relative to the player's own grown max, not a fixed 20 (a judgment call, flagged in decisions.md). True max grows from vanilla's 20 points (10 icons) up to 60 (30 icons) as Survivalist levels. `HungerOverlay` replaces vanilla's bar entirely via `RegisterGuiLayersEvent#replaceLayer(VanillaGuiLayers.FOOD_LEVEL, ...)`, reusing vanilla's own icon sprites — no mixin needed anywhere, for either the mechanic or the display. Cook (renamed from the old "Chef" placeholder) boosts cooked-food restoration, XP'd on eating a cooked item specifically (a filled-in assumption — "XP from cooking" was considered and rejected over multiplayer furnace-ownership ambiguity). 6 new unit tests for `PlayerHunger`'s pure clamping logic; the tick/eating mechanism itself isn't unit-testable (needs a live `ServerPlayer`). Boot-smoke-tested clean via `runServer`/`runClient`; **in-game behavior (eating, regen, starvation, sprint-lock, overlay look) not yet confirmed**. This work also inserted a new Section 10 into design-document.md and renumbered everything after it (old 10→11 through 15→16) — see decisions.md for the full mapping before trusting an old cross-reference's section number.

**Second round of Survivalist/Cook playtest fixes, 2026-09-24** — see [context/decisions.md](context/decisions.md). Real in-game testing surfaced four issues, three fixed:
- **Attachment sync bug (real, affected every skill)**: mutating an object returned by `getData()` does not trigger a client resync in NeoForge — only `setData`/`removeData` do. This silently broke the hunger overlay and likely Lumberjack/Miner's `SpeedMultiplier` too, undetected until now. Fixed by adding explicit `player.syncData(...)` calls after every in-place mutation of `PLAYER_HUNGER` (`HungerListener`, `DebugCommands`) and `PLAYER_SKILLS` (centrally in `api.Lyfe#addXp`, covering all skills at once).
- **Full-eating not blocked**: decoupling hunger broke vanilla's own "can't eat when full" check, since it only ever sees the pinned real food level. Fixed with a new `HungerListener#onUseItemStart` that cancels `LivingEntityUseItemEvent.Start` for non-`canAlwaysEat()` food at true-max.
- **Burn-kill Cook XP attribution**: originally checked the killing blow's damage-source entity, which misses "ignited with Fire Aspect, then died later purely from burning" (no entity on that final source). Fixed to use `LivingEntity#getLastHurtByPlayer()` — vanilla's own general kill-credit tracking (100-tick memory), which covers this case correctly.
- **Not fixed, documented as a known limitation**: the hunger overlay's icons overlap the oxygen bubble HUD while swimming. Vanilla positions air bubbles via a private, stateful field (`Gui#rightHeight`) that only vanilla's own HUD layers coordinate through — a custom `GuiLayer` can't participate without also replacing air-bubble rendering. Deferred, tied to a future **Swimmer** skill (more bubbles past vanilla's cap, swim speed) that would need the same custom-overlay treatment `HungerOverlay` uses.
- Debug commands (`/lyfe xp`, `/lyfe hunger`) also stopped working mid-testing; root cause pragmatically resolved by lowering `DebugCommands`' permission from gamemaster to `LEVEL_ALL` rather than continuing to chase why `ops.json` didn't take effect as expected — see decisions.md for the full debugging trail.

**Confirmed live, 2026-09-24**: `/lyfe` commands work and the burn-then-later-death Cook XP trigger fires correctly. Survivalist & Cook (Phase 2.5) considered done for now; the oxygen-bubble overlap remains an open, documented limitation deferred to a future Swimmer skill.

**`.location` overlay now renders one line per Cartographyr Layer, 2026-09-24** (see [context/decisions.md](context/decisions.md)) — Cartographyr gained an open, trust-based `Layer` registry (id + label + placement); Cartographyr owns only the registry as data, Lyfe owns all rendering. `LocationTracker` now groups detected entities by `layerId` instead of picking one arbitrary entity, preferring `CONSTRUCTED` over `NATURAL` within the shared built-in `Location` layer (a settlement inside its own surrounding natural region). `LocationPayload`/`ClientLocationState`/`LocationOverlay` all reshaped from a single string to a placement-sorted `List<LocationLine>`, rendered as a stacked block (highest placement on top, `Location` at placement 0 on the bottom, per the user's spec). Boot-smoke-tested clean with both mods loaded; **real in-game confirmation of actual multi-line stacking is still pending** — no second layer (e.g. a Territory mod) exists yet to exercise it, only the single `Location` line has been exercised so far.

**Persisted player knowledge, Cartographyr/Historian skills, sign/map mechanic implemented 2026-09-24** (design doc Section 9, Phase 4/5) — see [context/decisions.md](context/decisions.md). New `.knowledge` package: `PlayerKnowledge` (the real thing `.location` was a stand-in for — `LocationPrecision`/`KnowledgeEntry` model Section 9.3's Unknown/Relative/Approximate/Exact/Named/Visited/Historically-Known table exactly), `KnowledgeReference` (embedded sign/map data), `SignListener` (placement/reading), `WritingScreen`/`OpenWritingScreenPayload`/`SubmitWritingPayload`/`ClientWritingRequest`/`WritingTarget` (the authoring dialog and its networking). `location.LocationTracker` now calls `PlayerKnowledge#markVisited` for everything it detects before displaying it — physical presence auto-grants exact knowledge, so the overlay is knowledge-gated by construction, resolving the "honest simplification" flagged in the two previous rounds. `Skills.java` gained `CARTOGRAPHYR_ID`/`HISTORIAN_ID` (Knowledge category, gated on Cartographyr, a new slower `slowCurve()`) — Historian has no XP mechanic yet at all, deferred until books/NPC dialogue exist (confirmed with the user).
- **Real fidelity simplification, confirmed with the user before building**: signs are real vanilla `Blocks.OAK_SIGN` blocks (not a new custom block/model), placed on the clicked fence post with a `KnowledgeReference` attached to the `SignBlockEntity` via a new NeoForge attachment; maps are a plain item with a display name, not a rendered minimap texture. Both fully functional, just not visually bespoke.
- **A real soft-dependency bug found and fixed during implementation**: `PlayerKnowledge`/`KnowledgeReference` originally used Cartographyr's `EntityId` type directly, but both back attachments/items registered **unconditionally** — their static `CODEC` initializers would have force-loaded Cartographyr classes on a Cartographyr-less server, a failure mode the established "only construct the consumer class conditionally" pattern doesn't protect against. Fixed by keying everything on a raw `long` instead, with conversion only at the two Cartographyr-gated consumer classes. **Verified empirically**: `runServer` booted clean both with Cartographyr's jar present and with it physically removed from `run/mods/`.
- 10 new unit tests (`PlayerKnowledgeTest`, `SignListenerTest`'s `levelCap`) — the rest of the mechanic (right-click events, real block/entity placement) isn't unit-testable, same limitation as `natural.NaturalRegionDiscovery` in Cartographyr. Boot-smoke-tested clean; **real in-game confirmation of the write/read/XP loop is still pending**.
